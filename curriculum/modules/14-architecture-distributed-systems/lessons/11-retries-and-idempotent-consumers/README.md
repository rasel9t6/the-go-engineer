# Retries and idempotent consumers

## Learning objective

Implement at-least-once delivery semantics with idempotency keys, build a deduplication store, and apply exponential backoff retry logic in Go consumers.

## Why this matters

Distributed systems fail. Networks partition, brokers crash, consumers restart. Message delivery guarantees matter because every failure mode is possible: a message may be lost, delivered once, or delivered many times. At-least-once delivery is the most common broker guarantee -- it means the message is never lost, but it may be delivered more than once. Without idempotent consumers, duplicate messages cause double charges, duplicate emails, and corrupted state. Every production payment system, notification service, and order processor must handle this. Retries with backoff ensure transient failures are tolerated without hammering the downstream service.

## Mental model

Imagine mailing a letter. You put it in the mailbox (send). The postal service promises to deliver it at least once. If the recipient's mail carrier drops the letter, the postal service picks it up and re-delivers it. The recipient might receive two copies. To avoid problems, the recipient checks each letter's unique serial number. If they already processed that serial number, they throw the duplicate away. This is idempotency. The serial number is the idempotency key. The recipient's check is the dedup store.

Retries are analogous to knocking on a door again if nobody answers. Wait a short time, knock again. If still no answer, wait longer. This is exponential backoff. Adding random variation (jitter) prevents the "thundering herd" problem where all retries arrive simultaneously after a service outage.

## Core idea

**Idempotency**: an operation is idempotent if processing it multiple times produces the same result as processing it once. `SET balance = 100` is idempotent. `ADD balance + 10` is not.

**Idempotency key**: a unique identifier for an operation, generated by the producer and sent with the message. The consumer stores processed keys and rejects duplicates.

**At-least-once delivery**: the broker guarantees that every published message is delivered to at least one consumer. It may deliver the same message multiple times (e.g., if the consumer acknowledges after a crash and re-connects).

**Exponential backoff**: after a failed attempt, wait `base * 2^(attempt-1)` before retrying. With base 100ms: 100ms, 200ms, 400ms, 800ms, 1.6s, ... A maximum cap prevents infinite waits.

## Under the hood

An idempotency-aware consumer pipeline:

1. Receive message with idempotency key `K`.
2. Acquire distributed lock on `K` (e.g., Redis `SETNX`) to prevent concurrent processing.
3. Check dedup store for `K`. If found, acknowledge and skip.
4. Process the message (business logic + database writes).
5. Store `K` in dedup store with TTL (expiry) to prevent future duplicates.
6. Release lock and acknowledge the broker.

The dedup store must be durable and consistent. Options:

| Store | Characteristics |
|---|---|
| Redis with TTL | Fast, automatic expiry, but data loss on failover |
| PostgreSQL unique constraint | Durable, ACID, but slower |
| In-memory map | Fastest, but lost on restart -- acceptable for best-effort dedup |

## How Go uses it

- **`net/http` client retry**: many Go HTTP clients (e.g., `hashicorp/go-retryablehttp`) wrap the standard client with exponential backoff.
- **Kafka consumer libraries**: Sarama, Confluent-Go, and segmentio/kafka-go all surface idempotency via consumer group rebalancing. At-least-once is the default.
- **Payment gateways**: Stripe's API uses idempotency keys. Sending the same `Idempotency-Key` header produces the same result, even if the request is retried.
- **`github.com/cenkalti/backoff`**: the de facto Go library for exponential backoff with jitter.

## Go example

```go
package main

import (
	"fmt"
	"math/rand"
	"sync"
	"time"
)

type DedupStore struct {
	mu   sync.Mutex
	seen map[string]bool
}

func NewDedupStore() *DedupStore {
	return &DedupStore{seen: make(map[string]bool)}
}

func (d *DedupStore) TryProcess(key string) bool {
	d.mu.Lock()
	defer d.mu.Unlock()
	if d.seen[key] {
		return false
	}
	d.seen[key] = true
	return true
}

type RetryConfig struct {
	MaxAttempts int
	BaseDelay   time.Duration
	MaxDelay    time.Duration
}

func Retry(cfg RetryConfig, op func() error) error {
	var lastErr error
	for attempt := 1; attempt <= cfg.MaxAttempts; attempt++ {
		if err := op(); err != nil {
			lastErr = err
			if attempt == cfg.MaxAttempts {
				break
			}
			delay := cfg.BaseDelay * (1 << uint(attempt-1))
			if delay > cfg.MaxDelay {
				delay = cfg.MaxDelay
			}
			jitter := time.Duration(rand.Int63n(int64(delay))) / 2
			time.Sleep(delay/2 + jitter)
			continue
		}
		return nil
	}
	return lastErr
}

var attemptCount int
var mu sync.Mutex

func flakyHandler(n int) error {
	mu.Lock()
	attemptCount++
	count := attemptCount
	mu.Unlock()
	if count < n {
		return fmt.Errorf("transient error (attempt %d)", count)
	}
	return nil
}

func main() {
	store := NewDedupStore()
	keys := []string{"pay-1", "pay-2", "pay-1", "pay-3", "pay-2"}
	for _, k := range keys {
		if store.TryProcess(k) {
			fmt.Printf("processed: %s\n", k)
		} else {
			fmt.Printf("duplicate: %s\n", k)
		}
	}

	mu.Lock()
	attemptCount = 0
	mu.Unlock()

	err := Retry(RetryConfig{MaxAttempts: 5, BaseDelay: 10 * time.Millisecond, MaxDelay: 100 * time.Millisecond}, func() error {
		return flakyHandler(3)
	})
	if err != nil {
		fmt.Printf("retry failed: %v\n", err)
	} else {
		fmt.Println("retry succeeded")
	}
}
```

## Step-by-step execution

For `TryProcess` with keys `["pay-1", "pay-2", "pay-1"]`:

1. `TryProcess("pay-1")`: store.seen is empty. Insert `"pay-1"`. Return `true`.
2. `TryProcess("pay-2")`: store.seen has `"pay-1"` only. Insert `"pay-2"`. Return `true`.
3. `TryProcess("pay-1")`: store.seen has `"pay-1"`. Return `false`. The producer has the guarantee that `"pay-1"` was already handled.

For `Retry` with `flakyHandler(3)`:

1. Attempt 1: `flakyHandler` increments attemptCount to 1, returns error. Delay: 10ms/2 + 0..5ms jitter.
2. Attempt 2: attemptCount=2, returns error. Delay: 20ms/2 + jitter.
3. Attempt 3: attemptCount=3, returns nil. Retry returns nil, success.
4. If all 5 attempts fail, Retry returns the last error.

## Common mistakes

- **Storing idempotency keys without TTL**: keys accumulate forever, consuming memory and slowing lookups. Set a TTL of 24-72 hours, which covers the maximum redelivery window.
- **Ignoring concurrent duplicate processing**: two goroutines may receive the same message simultaneously. Both check the dedup store and both see a miss. Both process the message. Use a distributed lock (Redis `SETNX`) or a database unique constraint to prevent this.
- **Linear retry without backoff**: retrying every 100ms regardless of attempt number overwhelms the downstream service. Always use exponential backoff with jitter.
- **Infinite retries**: without a max attempt limit, a permanent failure retries forever, wasting resources. Set a reasonable cap (3-5 attempts) and route failed messages to a dead-letter queue.
- **Retrying non-retryable errors**: retrying a "400 Bad Request" is pointless. Only retry transient errors (5xx, timeouts, network errors).

## Debugging walkthrough

A payment service processes duplicate charges:

```go
func ProcessPayment(ctx context.Context, orderID string, amount int) error {
	return db.Exec("INSERT INTO charges (order_id, amount) VALUES ($1, $2)", orderID, amount)
}
```

**Symptom**: Customers are charged twice for the same order.

**Investigation**: The Kafka consumer receives the same message twice after a rebalance. The `INSERT` succeeds both times because there is no unique constraint on `order_id`. Check the consumer logs and broker offsets to confirm redelivery.

**Fix**: Add an idempotency key column with a unique constraint:

```go
func ProcessPayment(ctx context.Context, idempotencyKey string, orderID string, amount int) error {
	_, err := db.Exec(
		`INSERT INTO charges (idempotency_key, order_id, amount) VALUES ($1, $2, $3)
		 ON CONFLICT (idempotency_key) DO NOTHING`,
		idempotencyKey, orderID, amount,
	)
	return err
}
```

Now the second insert becomes a no-op. The database is the dedup store.

## Production notes

- **Dead-letter queue (DLQ)**: after exhausting retries, route the message to a separate queue for manual inspection. Never drop messages that fail all retry attempts.
- **Observability**: monitor retry count, idempotency key hit rate, and dedup store size. A high hit rate may indicate excessive redelivery due to consumer timeouts.
- **TTL sizing**: set idempotency key TTL to at least twice the maximum redelivery window. For Kafka, this is typically `max.poll.interval.ms + session.timeout.ms` -- about 5-10 minutes. Use 24 hours for safety.
- **Key generation**: idempotency keys must be unique per operation. Use UUIDv4, `ulid`, or a hash of the request body + timestamp.

## Performance implications

- **Dedup store lookup cost**: in-memory map lookup is O(1), ~20ns. Redis `SETNX` is ~1ms network round trip. PostgreSQL unique constraint check is ~5ms. Choose based on throughput requirements.
- **Backoff overhead**: sleeping the goroutine is cheap for millisecond delays. For second-scale delays, the goroutine is parked by the runtime and does not consume CPU.
- **Jitter prevents thundering herd**: without jitter, N retries from N consumers all fire at the same time, causing a CPU spike on the downstream service. Jitter spreads them across a time window.
- **Dedup store memory**: storing 1 million keys at 100 bytes each uses 100 MB. With TTL-based expiry, the store grows to a steady state equal to the TTL window's request volume.
