# Refresh tokens

## Learning objective

Implement a secure refresh token rotation flow in Go with short-lived access tokens, long-lived refresh tokens, rotation on use, revocation, and secure storage using cryptographic hashing and HMAC.

## Why this matters

Access tokens must be short-lived to limit the damage if stolen (typically 15 minutes). But users should not have to log in every 15 minutes. Refresh tokens solve this by providing a long-lived credential (30 days) that can safely obtain new access tokens. Refresh token rotation ensures that a stolen refresh token becomes useless once the legitimate user rotates it. This pattern is used by all major auth systems (GitHub, Auth0, Keycloak, Firebase). Go engineers building authentication systems must implement refresh token rotation correctly and securely.

## Mental model

Access tokens are hotel room keys. They expire at checkout (15 minutes). If someone steals your room key, they can only access your room until checkout.

Refresh tokens are the front desk. You show your ID (the refresh token) to get a new room key. If someone steals your ID, rotating the lock (getting a new ID) renders theirs useless.

With rotation: every time you use the refresh token, you get a new one and the old one is invalidated. If an attacker steals a refresh token and uses it, the legitimate user's next request will fail (the token is already rotated), alerting them to the compromise.

## Core idea

Refresh token flow:

1. User logs in with credentials. Server returns: `{access_token, refresh_token, expires_in}`.
2. Client uses `access_token` for API requests until it expires (401).
3. Client calls `POST /auth/refresh` with `refresh_token`.
4. Server validates the refresh token, issues a new access token and a new refresh token, and invalidates the old refresh token.
5. Client updates stored tokens and continues.

| Token type | Lifetime | Stored where | Revocable |
|---|---|---|---|
| Access token | 15 min | Client memory (or secure cookie) | No (until expiry) |
| Refresh token | 30 days | Server database + client secure storage | Yes |

Rotation security properties:
- **Single-use**: Each refresh token can be used exactly once.
- **Reuse detection**: If a used refresh token is presented again, the server can detect a potential token theft and revoke all tokens for that user.
- **Revocation**: Server can invalidate all refresh tokens for a user (e.g., on password change).

## Under the hood

Refresh tokens should be opaque, cryptographically random strings generated by `crypto/rand`. Never use `math/rand` for token generation.

The token is stored in the database as an HMAC-SHA256 hash of the raw token, not the raw token itself. This ensures that a database breach does not expose valid refresh tokens.

```text
Token generation:
  raw := crypto/rand(64 bytes) → hex-encoded string (128 chars)

Storage:
  hash := HMAC-SHA256(serverKey, raw) → hex string
  store(hash, userID, expiresAt, revoked=false)

Validation:
  hash := HMAC-SHA256(serverKey, raw)
  info := lookup(hash)
  if info.revoked or info.expired → reject
  return info.userID

Rotation:
  hash := HMAC-SHA256(serverKey, raw)
  info := lookup(hash)
  delete(hash)
  issue new tokens
```

The HMAC key is a server-side secret. Different services use different keys.

## How Go uses it

Go implementations of refresh token rotation typically use:

- `crypto/rand` for token generation
- `crypto/hmac` + `crypto/sha256` for token hashing
- `database/sql` with transactions for atomic rotation
- `sync.RWMutex` for in-memory stores (single-instance) or Redis for distributed stores

The rotation must be atomic: validate token, delete old token, create new token -- all in a single transaction or mutex-protected operation. Without atomicity, a race condition could allow both the legitimate user and an attacker to use the same token.

## Go example

```go
package main

import (
	"crypto/hmac"
	"crypto/rand"
	"crypto/sha256"
	"encoding/hex"
	"fmt"
	"sync"
	"time"
)

type RefreshTokenStore struct {
	mu      sync.RWMutex
	tokens  map[string]*RefreshTokenInfo
	hmacKey []byte
}

type RefreshTokenInfo struct {
	UserID    string
	ExpiresAt time.Time
	Revoked   bool
}

func NewRefreshTokenStore() *RefreshTokenStore {
	key := make([]byte, 32)
	rand.Read(key)
	return &RefreshTokenStore{
		tokens:  make(map[string]*RefreshTokenInfo),
		hmacKey: key,
	}
}

func (s *RefreshTokenStore) hashToken(token string) string {
	h := hmac.New(sha256.New, s.hmacKey)
	h.Write([]byte(token))
	return hex.EncodeToString(h.Sum(nil))
}

func (s *RefreshTokenStore) Issue(userID string, refreshTTL time.Duration) (string, error) {
	raw := make([]byte, 64)
	_, err := rand.Read(raw)
	if err != nil {
		return "", err
	}
	token := hex.EncodeToString(raw)

	hash := s.hashToken(token)
	s.mu.Lock()
	s.tokens[hash] = &RefreshTokenInfo{
		UserID:    userID,
		ExpiresAt: time.Now().Add(refreshTTL),
	}
	s.mu.Unlock()
	return token, nil
}

func main() {
	store := NewRefreshTokenStore()
	token, _ := store.Issue("user-abc", 30*24*time.Hour)
	fmt.Println("Refresh token issued:", token[:16]+"...")
}
```

## Step-by-step execution

For a refresh token rotation with reuse detection:

1. User logs in. Server issues access token (15 min) and refresh token (30 days). Store hash in database.
2. After 15 minutes, client receives 401. Client calls `POST /auth/refresh` with the refresh token.
3. Server hashes the refresh token with HMAC, looks up in database. Found, valid, not expired, not revoked.
4. Server atomically deletes the old token hash and inserts a new token hash. Returns new access token and new refresh token.
5. Client stores the new tokens and retries the original request.

**Attack scenario -- token theft:**

1. Attacker steals the user's refresh token (e.g., via XSS or device compromise).
2. Attacker calls `POST /auth/refresh` with the stolen token. Server rotates it. Attacker gets new tokens.
3. Legitimate user's next API call gets 401. User calls `POST /auth/refresh` with their (now-stale) refresh token.
4. Server looks up the hash... but the old token was deleted in step 2. The user's refresh fails.
5. Server detects reuse of an already-rotated token. This is a signal of token theft.
6. Server can revoke ALL tokens for this user and force re-login.

**Without rotation:**
1. Attacker steals refresh token. Both attacker and user can use it for 30 days.
2. There is no way to detect the theft.
3. The only mitigation is to shorten the refresh token lifetime.

## Common mistakes

- Mistake: Storing refresh tokens in the same database as access tokens without isolation.
  - Why it happens: Developers use one table for all tokens.
  - Fix: Refresh tokens have different security requirements (longer lifetime, revocable). Store them in a separate table with access controls.

- Mistake: Not rotating refresh tokens on each use, allowing unlimited reuse of stolen tokens.
  - Why it happens: Developers treat refresh tokens like access tokens (valid until expiry).
  - Fix: Always rotate. Each use creates a new refresh token and invalidates the old one.

- Mistake: Using opaque bearer tokens without a revocation check, making logout impossible.
  - Why it happens: Developers validate the signature but not revocation status.
  - Fix: Always check revocation status on each refresh. Maintain a deny list for revoked tokens.

- Mistake: Generating tokens with `math/rand` instead of `crypto/rand`.
  - Why it happens: Developers use the more familiar `math/rand` for simplicity.
  - Fix: Always use `crypto/rand` for security-sensitive tokens. `math/rand` is predictable.

- Mistake: Storing raw tokens in the database instead of hashed tokens.
  - Why it happens: Developers store the token directly for easy queries.
  - Fix: Store HMAC-SHA256 hashes. A database breach should not expose valid tokens.

## Debugging walkthrough

Consider this broken refresh token implementation:

```go
func (s *Store) Rotate(token string) (*TokenPair, error) {
	info, ok := s.tokens[token] // Raw token as key!
	if !ok {
		return nil, fmt.Errorf("invalid token")
	}
	delete(s.tokens, token)
	return s.Issue(info.UserID), nil
}
```

Symptom: Refresh token validation works initially, but after the server restarts, all previously issued tokens are invalid.

Investigation: The store uses an in-memory map. On restart, the map is empty.

Root cause: In-memory token storage without persistence. All tokens are lost on restart.

Fix: Persist tokens in a database. Load them on startup:

```go
// On startup, load all non-expired, non-revoked tokens from DB
func NewStore(db *sql.DB) *Store {
	rows, _ := db.Query("SELECT token_hash, user_id, expires_at FROM refresh_tokens WHERE revoked = false AND expires_at > NOW()")
	// ... populate map
}
```

But wait, the original code uses the raw token as the map key, which is also wrong:

Root cause (second): The code stores the raw token as the key instead of an HMAC hash. A database breach would expose all raw tokens.

Fix: Always hash tokens before storage:

```go
func (s *Store) hashToken(token string) string {
	mac := hmac.New(sha256.New, s.hmacKey)
	mac.Write([]byte(token))
	return hex.EncodeToString(mac.Sum(nil))
}

func (s *Store) Rotate(rawToken string) (*TokenPair, error) {
	hash := s.hashToken(rawToken)
	info, ok := s.tokens[hash]
	// ...
}
```

## Production notes

- Store refresh token hashes in a database table with `token_hash`, `user_id`, `expires_at`, `revoked`, and `created_at` columns.
- Create an index on `token_hash` for fast lookups.
- Use database transactions for atomic rotation: `BEGIN; DELETE WHERE hash=X; INSERT ...; COMMIT`.
- Implement reuse detection: if a rotated token is presented again, log the event and revoke ALL tokens for that user.
- Set appropriate TTLs: access tokens 15 minutes, refresh tokens 30 days (or as required by your security policy).
- Provide a `/auth/revoke-all` endpoint for password changes and security incidents.
- Use `crypto/rand` for all token generation. Generate at least 64 bytes (512 bits) of randomness per token.

## Performance implications

- Token generation with `crypto/rand` adds microseconds per issue.
- HMAC-SHA256 hashing is fast (hardware-accelerated on modern CPUs).
- Database lookup by token hash is O(log n) with proper indexing.
- The main performance bottleneck is the database transaction for rotation. Use connection pooling to minimize overhead.
- For high-throughput systems, consider batching token cleanup queries (deleting expired tokens) as a background job.
