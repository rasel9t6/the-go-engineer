# Reading stack traces

## Mission

Understand and apply Reading stack traces in the context of professional Go software engineering.

## Prerequisites

- core-06-11

## Mental Model

A stack trace is a breadcrumb trail from where the program crashed back to where it started. The top frame is the crash site. Each frame below is one step in the call chain. Read top to bottom to trace execution backwards.

## Visual Model

```text
input -> concept boundary -> behavior -> observable result
```

## Machine View

Stack traces are generated by the runtime's stack walking code. Each frame stores the program counter and stack pointer. The runtime walks the linked list of frames, resolving program counters to function names and line numbers via the symbol table.

## Code Walkthrough

Read the code from top to bottom. Connect each line to the mental model above. The important question is not only what the line does, but why the program needs that line.

## Try It

1. Run the command exactly as shown.
2. Change one input.
3. Predict the output before running again.
4. Explain the result in your own words.

Common mistakes:

- Ignoring the stack trace and searching for the bug by reading code randomly.
- Not recognizing that the top of the stack trace is the panic location.
- Getting confused by the goroutine label and assuming it's part of the call trace.
- Not looking at file and line numbers in stack traces.

## In Production

Stack traces are the first thing developers look at when a Go program crashes. Every production error monitoring tool (Sentry, Datadog) captures and displays stack traces. They're essential for post-mortem debugging.
