# Project layout

## Learning objective

Organise Go projects using standard layout conventions — flat layout, `cmd/`, `internal/`, and `pkg/` — and choose the right pattern based on project size and team structure.

## Why this matters

A well-organised project is easy to navigate, build, and contribute to. New team members can find the entry point, understand the architecture, and add code without guessing where files go. Standard Go layout conventions are recognised across the ecosystem — Kubernetes, Docker, Prometheus, and thousands of open-source projects follow them. Consistency reduces cognitive overhead and lets developers focus on logic, not directory structure.

## Mental model

Think of a Go project as a building with designated zones:

- **`cmd/`** — the lobby entrance. Each subdirectory is a standalone executable (a `main` package). Thin: just enough code to wire up dependencies and start the application.
- **`internal/`** — the employee-only area. Code here cannot be imported by external modules. This is where your business logic, domain types, and core services live.
- **`pkg/`** — the public conference room. Library code that is safe and intended for external consumption. Not all projects need this.
- **`go.mod`** — the building permit. Declares the module path and dependencies.
- **Root-level `.go` files** — rarely used in large projects, but fine for small libraries or single-file tools.

## Core idea

Go's project layout is not enforced by the compiler (except `internal/`). It is a set of conventions that the community has converged on.

### Flat layout (small projects)

```
mycli/
  go.mod
  main.go
  handler.go
  config.go
```

Best for: single-binary tools, small CLI utilities, libraries with one public package.

**Rule of thumb**: If you can keep all `.go` files in one directory with one `package main` (and maybe one library package), use flat layout.

### `cmd/` layout (medium projects)

```
myproject/
  go.mod
  cmd/
    server/
      main.go         → package main
    worker/
      main.go         → package main
  internal/
    server/
      handler.go      → package server
    db/
      postgres.go     → package db
    config/
      config.go       → package config
  pkg/
    apiclient/
      client.go       → package apiclient
```

Best for: multiple binaries sharing internal packages, production services.

### `internal/` + `pkg/` layout (large projects)

```
myproject/
  go.mod
  cmd/
    server/main.go
    worker/main.go
    cli/main.go
  internal/
    server/
    db/
    service/
    middleware/
  pkg/
    api/
      types.go
      handlers.go
    auth/
    validation/
  migrations/
  docs/
  scripts/
```

`internal/` contains packages that MUST NOT be imported outside the module. `pkg/` contains packages that CAN be imported by external modules.

### When not to use `pkg/`

Some in the Go community argue that `pkg/` is unnecessary noise — if you want a package to be importable, just put it at the root or in a descriptive top-level directory. The key insight: do not use `pkg/` as a dumping ground. Every package should have a clear purpose.

## Under the hood

The `internal/` restriction is the only compiler-enforced layout rule. When the compiler resolves an import of a package containing `internal` in its path, it checks that the importer's package path shares the root of the `internal` directory's parent.

For example, with module `github.com/myorg/myproject`:

```
github.com/myorg/myproject/internal/db
  → can be imported by github.com/myorg/myproject/cmd/server
  → can be imported by github.com/myorg/myproject/pkg/api
  → cannot be imported by github.com/other/project
  → cannot be imported by github.com/myorg/otherproject
```

The compiler does not care about `cmd/`, `pkg/`, or any other top-level directory name. These are purely human conventions.

## How Go uses it

- **`cmd/`**: Each subdirectory produces a separate binary. `go install ./cmd/...` installs all of them.
- **`internal/`**: Encapsulation enforcement. Teams use it to prevent external consumers from depending on internal implementation details.
- **`pkg/`**: Signals that a package is stable and intended for public use. Not necessary, but widely adopted.
- **`vendor/`**: Contains vendored dependencies (generated by `go mod vendor`). Should be gitignored unless your team policy requires vendoring.
- **`_example/` or `example/`**: Example applications showing how to use the library.
- **`_scripts/` or `hack/`**: Build scripts, CI helpers, code generation.

## Go example

A minimal `cmd/server/main.go` in a well-structured project:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"os"

	"myproject/internal/config"
	"myproject/internal/server"
)

func main() {
	cfg := config.Load()
	mux := server.NewRouter(cfg)
	addr := fmt.Sprintf(":%s", os.Getenv("PORT"))
	log.Printf("server starting on %s", addr)
	log.Fatal(http.ListenAndServe(addr, mux))
}
```

And the project directory structure:

```
cmd/
  server/
    main.go
  worker/
    main.go
internal/
  config/
    config.go
  server/
    handler.go
    router.go
  worker/
    processor.go
pkg/
  apiclient/
    client.go        → public HTTP client for the server API
go.mod
go.sum
README.md
```

Each `cmd/*/main.go` is a thin `package main` that:
1. Parses flags / environment.
2. Initialises dependencies (config, database, logger).
3. Starts the application (HTTP server, worker loop).

## Step-by-step execution

Building and running from a standard layout:

1. `go build ./cmd/server` — compiles the `server` main package into an executable.
2. `go build ./cmd/worker` — compiles the `worker` main package into a separate executable.
3. `go build ./pkg/apiclient` — compiles the library package (no executable, verifies it compiles).
4. `go test ./internal/...` — runs all tests for internal packages.
5. `go vet ./...` — runs the Go vet analyser over all packages.

The `./...` wildcard matches all packages in the module, making it easy to build, test, and vet everything.

## Common mistakes

- **Flat layout with 20+ `.go` files in one directory**: Packages should be small. If your `package main` has 20 files, split into subpackages.
- **Multiple packages in one directory**: Go does not allow it. All `.go` files in a directory must declare the same package.
- **Putting business logic in `cmd/`**: `cmd/` should be thin. Business logic belongs in `internal/` or `pkg/`.
- **Unnecessary deep nesting**: 4+ levels of directory nesting is rare in Go. Keep it shallow (2-3 levels).
- **`pkg/` as a junk drawer**: Every package under `pkg/` should have a clear, focused responsibility. Do not throw random utilities there.
- **Confusing `internal/` scope**: `internal/` restricts to the module tree, not to the entire repository. Multi-module repos have separate `internal/` boundaries per module.
- **Not using `go mod tidy`**: After adding or removing imports, run `go mod tidy` to keep `go.mod` and `go.sum` consistent.

## Debugging walkthrough

Symptom: `go run .` fails with:

```
package main is not a package in the directory .../cmd/server
```

**Root cause**: Running `go run .` in the project root, but the main package is at `cmd/server/`, not the root.

**Fix**: Use the correct path:
```bash
go run ./cmd/server
```

Or, if you want to run from the project root:
```bash
go run ./curriculum/modules/05-types-interfaces-packages-modules/labs/17-project-layout/cmd/server
```

Symptom: `go build ./internal/...` fails with:

```
import ".../internal/config" is not allowed from ".../some/other/module"
```

**Root cause**: Another module is trying to import your `internal` package. Only packages within your module can do so.

**Fix**: If the importer should have access, move the package out of `internal/` into `pkg/` or the root.

## Production notes

- **Standard layout is not required but recommended**: The Go team does not mandate a layout, but the ecosystem conventions make onboarding easier.
- **Don't fight your tools**: Use `goimports` for automatic import management. Use `golangci-lint` to enforce consistency.
- **Monorepo considerations**: In a monorepo with multiple Go modules, each module can have its own layout. Use `go.work` for local development across modules.
- **Generated code**: Place generated code in a `gen/` or `_gen/` directory, or alongside the source it extends (e.g., `internal/api/gen/`).
- **Avoid `src/` directory**: Unlike `GOPATH` mode, module mode does not need `src/`. Top-level `src/` is uncommon in Go projects.
- **Document your layout**: A brief `README.md` at the project root explaining the directory structure saves time for new contributors.

## Performance implications

- Project layout has zero runtime impact — it is a source-code organisation concern.
- Build times can be affected by package count and import graph depth, but layout choices rarely matter. Use `go build -v` to see compilation order.
- The linker and compiler do not care about directory names; they only care about package paths and import graphs.
- `internal/` provides real encapsulation at compile time, preventing dependency creep that would otherwise increase binary size.
